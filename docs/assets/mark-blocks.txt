lode mark -- Unicode block-character redraw (lode-fhql.4, feeds lode-fhql.5)

Derived directly from docs/assets/mark.svg's own 8x8 grid: every coordinate
in that SVG (viewBox 0 0 32 32, 4-unit cells) is a multiple of 4, so the
SVG's own path IS this grid -- this file rasterizes it cell for cell,
rather than reinterpreting the mark. Reproduced with the same
toolchain as mark-16.png (scripts/rasterize-mark.sh, cairosvg): rendered
mark.svg at 80x80px (10px per cell) -- `scripts/rasterize-mark.sh 80`,
which writes an uncommitted mark-80.png -- and sampled the centre pixel of
each of the 64 cells. A cell centre lands on a rect's low edge but not its
high edge, so the sampling is half-open and the grid is exact rather than
an eyeballed approximation.

The two grids below are the same 64 cells twice: the Unicode redraw is a
pure glyph substitution of the ASCII proof grid, gated by
tests/test_brand_assets.py. Edit one and you must edit the other.

Legend, 8 columns by 8 rows, row 0 at top (matching the SVG's own y axis):

    v = vein   (the bold zigzag stroke)
    s = strata (one of the three receded horizontal bands)
    . = empty

ASCII proof grid (one character per cell, no separators, 8 chars/row):

.....vv.
sssssvss
.....v..
..vvvv..
ssvsssss
..v.....
vvvsssss
........

Unicode block redraw -- the same 64 cells, one glyph per cell, monospace
only, copy/paste safe. Empty cells use a middle dot rather than a plain
space so every row stays exactly 8 columns wide even if trailing
whitespace gets stripped by an editor or a git diff.

CAVEAT for lode-fhql.5: all three glyphs (U+2588, U+2591, U+00B7) are East
Asian Ambiguous width, so a terminal configured to render ambiguous-width
characters double-wide will stretch the grid to 16 columns. That is a
terminal-side setting, not something this file can encode -- a consumer
that must be width-exact everywhere needs its own fallback.

    v -> █ FULL BLOCK   (foreground: the vein)
    s -> ░ LIGHT SHADE  (background: strata)
    . -> · MIDDLE DOT   (empty)
